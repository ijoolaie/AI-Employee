# W10 ZarinPal Revenue Certification Runbook

## Purpose

This runbook is the final operational procedure for proving the first real revenue outcome generated by the AI Workforce through ZarinPal.

This document does **not** claim that a real ZarinPal payment has been executed. Until the certification workflow completes with real provider evidence, the status remains:

> **W10 ZarinPal Revenue Certification: NOT VERIFIED**

## Current gate

The repository already contains the governed ZarinPal payment path and a manual-only live certification workflow.

Current blocker:

- Real `ZARINPAL_MERCHANT_ID` is not available.
- A real reachable server/callback environment is not yet available for production certification.
- No real ZarinPal checkout, verification, or revenue event has therefore been evidenced.

Do not replace missing provider evidence with synthetic tests. Synthetic reconciliation tests prove internal behavior only.

## Evidence boundary

### What can be verified without ZarinPal credentials

- ZarinPal adapter unit/contract tests.
- Amount conversion and validation.
- Callback handling tests.
- Provider selection and governance tests.
- Synthetic revenue reconciliation/idempotency tests.
- Python compilation/static checks.
- Full CI gates.

### What cannot be certified without real provider access

- Real ZarinPal payment request acceptance.
- Real checkout URL usability.
- Real customer payment.
- Independent server-side ZarinPal verification.
- Real provider reference ID.
- Real revenue event produced from a verified provider payment.
- **First Revenue Generated by AI Workforce**.

## Required environment

### Sandbox certification

Minimum:

- GitHub Actions access with repository secrets configured.
- A valid ZarinPal sandbox merchant ID.
- The repository workflow can reach the ZarinPal sandbox from the runner.
- An operator/customer able to complete the sandbox payment manually.

The workflow defaults to sandbox mode.

### Production certification

Important distinction: the current GitHub Actions workflow is a **live provider integration certification runner** built on an ephemeral Docker Compose stack. Even with `sandbox=false`, a successful run of that workflow alone does **not** prove that the deployed production application generated revenue. Production revenue evidence requires the payment to be created and reconciled by the actual deployed production environment (or its durable production data plane), with the production run/job evidence retained.

Additionally required:

- Production ZarinPal merchant ID.
- A publicly reachable HTTPS callback URL.
- Production application/server environment.
- Explicit operator authorization to create a real payment checkout.
- A real customer/payment method and explicit approval to charge the certification amount.

Never place the merchant ID in source control, commit messages, logs, or this document.

## GitHub Actions secrets

Configure repository/environment secrets as appropriate:

- `ZARINPAL_MERCHANT_ID`
- `ZARINPAL_CALLBACK_URL` — required for production; must be HTTPS.
- `W10_ZARINPAL_CERTIFICATION_EMAIL`

The workflow also accepts runtime inputs for:

- `sandbox`
- `amount_irr`
- `wait_minutes`
- `confirm_external_payment`

The confirmation input must exactly equal:

`I_UNDERSTAND_THIS_CREATES_A_REAL_ZARINPAL_CHECKOUT`

This confirmation is required because the workflow creates an external payment checkout.

## Certification procedure

### Phase A — Preflight

1. Confirm the target commit is the intended current `main` commit.
2. Confirm normal CI is green for that commit.
3. Confirm the ZarinPal merchant credential is available through GitHub Secrets.
4. Confirm the intended mode:
   - `sandbox=true` for first certification.
   - `sandbox=false` only for an explicitly approved production certification.
5. Confirm the certification amount.
6. For production, confirm the callback URL is public HTTPS.
7. Confirm no card credentials will be entered into automation.

### Phase B — Sandbox certification

Run the GitHub Actions workflow:

`.github/workflows/workforce-w10-live-zarinpal-payment.yml`

Recommended initial inputs:

- `sandbox=true`
- `amount_irr=100000` or another approved test amount >= 10000
- `wait_minutes=20`
- `confirm_external_payment=I_UNDERSTAND_THIS_CREATES_A_REAL_ZARINPAL_CHECKOUT`

The workflow performs:

1. Configuration validation.
2. W10 stack startup.
3. Database migration/check.
4. Health check.
5. ZarinPal provider configuration check.
6. Python compilation.
7. ZarinPal contract tests.
8. Real ZarinPal checkout creation.
9. Manual payment window.
10. Direct server-side verification against ZarinPal.
11. Provider-neutral revenue reconciliation.
12. Evidence output containing deal/order/provider reference identifiers.
13. Cleanup.

The payment itself is manual. The runner must never receive card credentials.

### Phase C — Production certification

Production is a separate controlled step.

Before starting:

- Obtain explicit approval for the real certification amount.
- Set `sandbox=false`.
- Configure a real production merchant ID.
- Configure a public HTTPS callback URL.
- Confirm the server/application environment is production-ready.
- Confirm the customer/operator understands that this is a real charge.

Only then run the controlled production payment flow against the deployed production environment. The existing GitHub Actions workflow may be used as a provider/integration certification step, but its ephemeral test database must not be counted as production revenue evidence.

## PASS criteria

A production revenue certification may be marked **PASS** only when the workflow evidence demonstrates all of the following:

1. The real provider request was accepted.
2. A real ZarinPal authority was returned.
3. The checkout was actually completed by the customer/operator.
4. Server-side verification against ZarinPal succeeded.
5. ZarinPal returned a real provider reference ID.
6. The verified amount matches the certification deal.
7. The verified payment reconciled into `WorkforceRevenueEvent`.
8. Tenant/deal correlation is preserved.
9. The resulting order/revenue record is persisted.
10. The GitHub Actions run is successful.
11. Logs/artifacts contain sufficient evidence to independently identify the run and outcome without exposing secrets.

Only after all of these are evidenced may the KPI be updated to:

> **First Revenue Generated by AI Workforce — VERIFIED**

## Failure handling

### Missing merchant ID

Expected result:

> Certification blocked before external payment.

Status:

> `NOT RUN` / `NOT VERIFIED`

Do not substitute a fake merchant ID.

### Provider request fails

Record:

- workflow run ID
- commit SHA
- provider mode
- HTTP/provider error category
- timestamp

Do not mark revenue as generated.

### Payment is not completed before timeout

The certification remains unsuccessful for revenue purposes.

The created checkout/deal may exist, but:

> `First Revenue Generated by AI Workforce = NOT VERIFIED`

Do not manufacture a revenue event.

### Verification fails

Do not reconcile the payment as revenue.

The internal revenue path must remain fail-closed until independent provider verification succeeds.

### Reconciliation fails after provider verification

Treat this as an engineering incident/gap:

- preserve provider evidence;
- do not create a second synthetic revenue event manually;
- investigate idempotency/reconciliation;
- rerun only after the underlying issue is fixed.

## Stop/go decision

### STOP

Remain stopped at the revenue certification gate when any of these are missing:

- real merchant credentials;
- approved payment amount;
- reachable certification environment;
- required production HTTPS callback;
- explicit authorization for an external payment.

### GO

Proceed to sandbox certification when the sandbox merchant credential is available.

Proceed to production certification only after sandbox behavior is understood and the real production payment has explicit authorization.
