# AI Employee v1.4.5 Product Gap & Execution Plan

## Release context

`v1.4.4` is the current stable GitHub release baseline. This document defines the next execution scope as `v1.4.5` work; it is not a historical `v1.3.1` release document.

## Purpose

This document records the product gaps found during end-to-end verification and the execution scope for the next SaaS foundation work. The goal is to close functional gaps, not add speculative features.

## Confirmed gaps

### P0 — Tenant hierarchy, roles, plans and entitlements

The commercial hierarchy must be explicit and enforceable:

```text
Vendor / Platform
      |
      +--> Reseller
              |
              +--> Client
```

Required flows:

- Vendor provisions and manages Reseller organizations.
- Vendor defines the plans/packages available to Resellers.
- Reseller receives a plan/contract and its allowed limits/features.
- Reseller provisions Client tenants.
- Reseller defines the Client plan/contract within Vendor-approved constraints.
- Client receives only its own entitlements and tenant-scoped resources.
- Entitlements are enforced server-side; frontend visibility is only a reflection of server authorization.
- Plan changes, suspension/reactivation, expiration and quota exhaustion have explicit states and behavior.
- Usage metering is tied to the owning tenant and applicable plan/entitlement.

### P0 — Authorization and tenant isolation

A single permission matrix must cover Vendor, Reseller and Client scopes.

Requirements:

- No cross-tenant access by client-controlled tenant identifiers.
- Parent-to-child access is explicit and auditable.
- Resource actions check both actor permission and resource lifecycle state.
- Role/permission changes are audited.
- Tenant context is explicit in the UI when a user can operate across multiple organizations.
- Server-side authorization is authoritative for every API action.

### P0 — Resource lifecycle actions

Lifecycle controls must be implemented as real backend operations, not UI-only state changes.

Inventory and standardize applicable actions for:

- Runs / jobs
- Workflows / schedules
- Agents / employees
- Clients / tenants
- Users / memberships
- Integrations / connections
- Approvals where cancellation is meaningful

Common state model where applicable:

```text
created -> queued -> running -> success
                         |-> failed
                         |-> cancelled
```

For long-lived resources:

```text
active -> suspended -> active
active -> archived -> retained/deleted according to policy
```

Requirements:

- Stop/Cancel actually signals the backend execution when execution is active.
- Delete is used only where hard deletion is safe; otherwise Archive/Deactivate is preferred.
- Destructive actions require confirmation and authorization.
- Lifecycle transitions are idempotent.
- Every destructive or administrative transition is audited.
- UI actions are state-aware and hidden/disabled when invalid.

### P0 — Refresh and data synchronization

Every visible Refresh action must perform a real server refresh.

Requirements:

- Query/data invalidation or explicit refetch on click.
- Loading state during refresh.
- Error state with retry.
- Preserve filters, pagination and selected context when practical.
- Refresh dependent counters/status badges together with the primary list.
- Avoid duplicate concurrent refresh requests.
- Realtime/polling may be used where appropriate, but manual Refresh remains deterministic.

### P0 — Localization and Persian RTL

Persian support must be real localization, not only direction switching.

Requirements:

- Translation catalogs for `fa` and `en` with stable message keys.
- All navigation, buttons, dialogs, forms, tables, statuses, empty states, errors and validation messages use translation keys.
- `<html lang>` and `dir` are set from locale before/at render time.
- RTL uses CSS logical properties instead of hard-coded left/right layout assumptions.
- Directional icons, breadcrumbs, pagination and progress indicators are reviewed for RTL behavior.
- Date, time, number and currency formatting use locale-aware formatters.
- Mixed Persian/Latin technical values remain readable and correctly isolated where needed.
- Persian text expansion does not break buttons, tables or navigation.

### P1 — Tenant lifecycle and commercial operations

These are required to make Vendor -> Reseller -> Client operational rather than merely structural:

- onboarding/provisioning
- invitation and membership management
- ownership/admin transfer
- suspension/reactivation
- plan change with entitlement recalculation
- expiration/grace-period behavior
- offboarding/archive and data-retention policy
- usage/quota visibility
- billing/subscription status visibility

Hard deletion of a tenant is not the default operation. Retention and reactivation behavior must be defined before destructive tenant deletion is exposed.

### P1 — Shared UX state model

Across all major pages, standardize:

- loading
- empty
- error
- retry
- success feedback
- disabled/permission-denied state
- destructive-action confirmation
- unsaved-change protection where forms can lose data

This prevents each page from implementing lifecycle behavior differently.

### P1 — Accessibility and keyboard behavior

Because lifecycle controls and RTL affect interaction, verify:

- keyboard access to primary actions
- visible focus states
- accessible button names/tooltips
- dialog focus trapping and Escape behavior
- confirmation dialogs readable in RTL
- status information not conveyed by color alone

## Explicitly out of scope for this execution pass

Do not add speculative marketplace, advanced partner enablement, co-marketing, or complex regional infrastructure features unless an existing product requirement or implementation dependency requires them. They belong to later ecosystem/commercial phases.

## Execution order

1. Establish the Vendor -> Reseller -> Client authorization, tenant-context and entitlement model.
2. Implement lifecycle actions and shared Stop/Cancel/Delete/Archive semantics.
3. Implement Refresh/refetch infrastructure and shared loading/error/retry states.
4. Complete Persian localization and RTL correctness across the application shell and major pages.
5. Add tenant onboarding, suspension/reactivation, plan changes, expiration/grace and offboarding semantics.
6. Add/expand audit, usage/quota visibility and accessibility coverage.
7. Add backend, frontend and E2E regression tests for every completed capability.
8. Run Docker/runtime verification and production-like checks.

## Definition of Done

- Vendor -> Reseller -> Client hierarchy works end-to-end.
- Roles, permissions and entitlements are enforced server-side.
- Tenant isolation and parent-child access are tested.
- Stop/Cancel/Delete/Archive actions perform real lifecycle transitions.
- Refresh performs real data synchronization.
- Loading/error/retry/empty states are consistent.
- Persian UI is translated and correctly RTL, not merely mirrored.
- Tenant lifecycle and commercial state transitions are explicit and auditable.
- Accessibility checks cover primary actions and dialogs.
- Backend, frontend and E2E tests pass.
- Docker/runtime verification passes.
