## Scope verified in source

### WhatsApp provider-message idempotency

- `CustomerMessage.provider_message_id` persists the provider message identifier.
- Uniqueness is scoped to `tenant_id + channel_id + provider_message_id`.
- The unique index is partial and applies only when the provider identifier is non-null.
- Duplicate admission returns the existing conversation/run and does not create another Run.

### WhatsApp conversation admission

- WhatsApp conversations use `external_conversation_key = wa:<phone>`.
- Uniqueness is scoped to `channel_id + external_conversation_key`.
- PostgreSQL uniqueness is the final concurrency guard.
- Conversation creation handles `IntegrityError` inside a SAVEPOINT and then reads the winning row.
- Legacy conversations without the new key have a compatibility path using row locking.

### Transactional execution hand-off

- WhatsApp no longer calls Celery directly from the API transaction.
- The handler persists an `agent.run.execute` transactional-outbox row with the Run and message.
- The outbox dispatcher queues Celery only after the database transaction has committed.
- The outbox row has a deterministic WhatsApp dedupe key.

This closes the previously identified API-commit-versus-worker-start race.
