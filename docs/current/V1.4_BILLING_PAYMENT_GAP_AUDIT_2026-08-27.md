## Findings

### 1. No billing rewrite

The provider-neutral billing core already owns plans, subscriptions, quota enforcement, usage, lifecycle processing, event recording, and MRR reporting.

Rebuilding this would duplicate existing functionality and violate the V1.4 execution rule that only evidenced gaps become implementation work.

### 2. Stripe adapter exists

The repository already implements:

- Checkout Session creation;
- Billing Portal creation;
- Stripe webhook signature verification;
- event dispatch;
- provider-event idempotency;
- subscription updates;
- cancellation;
- failed-payment transition.

Therefore a generic “implement payments” PR is not justified.

### 3. External evidence remains the largest gap

The Stripe implementation explicitly records that real Stripe API calls and a real Checkout completion were not exercised from the original delivery environment.

This is an **external-evidence gap**, not proof that the architecture is missing.

### 4. Refund/reversal capability needs a targeted decision

The frozen V1.4 Blueprint names refunds among required payment capabilities, while the existing Stripe As-Built document explicitly defers refund handling.

This is the clearest repository-level functional gap identified by the audit.

Before implementation, the next PR must define:

- refund authority and RBAC;
- tenant/provider ownership checks;
- idempotency key/event semantics;
- full vs partial refund policy;
- provider adapter behavior;
- BillingEvent/audit trail;
- webhook reconciliation for refund/charge state;
- tests for duplicate/replayed provider events.
