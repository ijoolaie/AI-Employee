# V1.5 Step 12 — Marketplace Runtime Integration Plan

## Purpose

Connect the Marketplace/Developer ecosystem to the multi-tenant runtime without weakening tenant isolation, RBAC, billing, payment, or observability boundaries.

The repository already defines a Developer Console foundation with API keys, application registration, webhooks, usage analytics, integration settings, sandbox controls, scoped keys, RBAC, audit logs, and rate limits. Marketplace apps/plugins are identified as a future extension of that console. This step turns that architectural direction into a runtime integration boundary.

## Core Entities

### Marketplace App

Represents a publishable developer product.

Required attributes:

- id
- developer_id
- slug
- name
- description
- category
- status
- visibility
- current_version_id
- created_at
- updated_at

Statuses:

- DRAFT
- REVIEW
- PUBLISHED
- SUSPENDED
- RETIRED

### App Version

Immutable executable/manifest version.

Required attributes:

- id
- app_id
- version
- manifest
- runtime_contract
- checksum
- status
- created_at

Versions must be immutable after publication.

### Installation

Connects a marketplace app to a tenant.

Required attributes:

- id
- tenant_id
- app_id
- version_id
- installed_by
- status
- configuration
- installed_at
- uninstalled_at

Installation ownership is always tenant-scoped.

### App Permission Grant

Defines the capabilities granted by a tenant to an installed app.

Required attributes:

- id
- installation_id
- permission
- granted_by
- granted_at
- revoked_at

The runtime must never infer permissions from the app manifest alone; effective permissions are the intersection of declared capabilities and tenant grants.

## Runtime Invocation Rules

Every invocation must carry:

- tenant_id
- installation_id
- app_id
- app_version_id
- user_id when user initiated
- request_id / trace_id
- effective permissions

Invocation is rejected when any of these conditions is true:

- tenant context is missing
- installation does not belong to the current tenant
- installation is inactive
- requested capability was not granted
- app version is not executable
- tenant plan does not include the capability
- rate or usage limit is exceeded

## Tenant Isolation

Marketplace data is tenant-aware by default.

A tenant can only:

- list its own installations
- read its own installation configuration
- grant/revoke its own app permissions
- invoke apps installed in that tenant
- view its own marketplace usage

A developer can only manage applications it owns or is explicitly authorized to manage.

Cross-tenant installation access is forbidden.

## Entitlement / Billing Integration

Marketplace capabilities may be gated by plan entitlements.

```text
Installation Request
        |
        v
Plan Entitlement Check
        |
   +----+----+
   |         |
 Allow     Reject
   |         |
   v         v
Install    Upgrade Required
```

Metered marketplace operations emit usage events such as:

- marketplace.install
- marketplace.invoke
- marketplace.api_call
- marketplace.storage
- marketplace.automation

Revenue-share accounting is intentionally kept separate from runtime authorization and can consume these immutable usage events later.

## Payment Integration Boundary

Marketplace runtime must not call payment providers directly.

```text
Marketplace
    |
    v
Billing / Revenue Service
    |
    v
Payment Abstraction
    |
    v
Provider Adapter
```

This preserves the existing provider abstraction and allows commissions, subscriptions, or one-time purchases to evolve independently.

## Security Model

Marketplace security is based on four independent checks:

1. Authentication
2. Tenant ownership / installation ownership
3. RBAC + app scope authorization
4. Plan entitlement / usage enforcement

The order is intentional:

```text
Authentication
 -> Tenant
 -> Installation
 -> Permission
 -> Entitlement
 -> Rate / Usage
 -> Runtime
```

## Testing Strategy

### Tenant Isolation

- Tenant A cannot read Tenant B installations.
- Tenant A cannot invoke Tenant B installations.
- Tenant A cannot alter Tenant B app configuration.

### Permission Isolation

- An installed app cannot call an undeclared capability.
- A declared capability without tenant grant is rejected.
- Revoked grants take effect immediately.

### Lifecycle

- Draft apps cannot be installed.
- Published versions are immutable.
- Suspended apps cannot execute.
- Uninstall revokes runtime access.

### Billing / Entitlement

- Plan-ineligible installation is rejected.
- Plan-ineligible invocation is rejected.
- Metered usage is emitted exactly once per accepted operation.

### Reliability

- Duplicate webhook delivery is idempotent.
- Duplicate invocation event processing does not double-count usage.
- Runtime failure produces an auditable failure event.

## Completion Criteria

- Marketplace registry exists.
- App versions are immutable.
- Tenant installations are isolated.
- Permission grants are explicit and revocable.
- Marketplace runtime invokes only authorized installations.
- Billing/entitlement checks are enforced before execution.
- Usage events feed the existing metering boundary.
- Webhooks are idempotent.
- Security and audit events are emitted.
- Cross-tenant and permission-isolation tests pass.
