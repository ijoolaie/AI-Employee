## Architecture principles

1. Dependency-first implementation.
2. Tenant isolation is foundational.
3. Authentication and authorization are separate concerns.
4. The server is authoritative for tenant, permission, entitlement, usage and payment state.
5. External AI and payment providers are accessed through internal adapters.
6. Financial and security operations are auditable.
7. External callbacks and usage events are idempotent.
8. Existing behavior and data are preserved through controlled migrations.
9. Planned, As-Built and Verified status are kept separate.

## Tenant runtime

```text
Request
 ↓
Authentication
 ↓
Tenant Resolution
 ↓
Tenant Context
 ↓
Authorization
 ↓
Business Service
 ↓
Repository / Database
```

Tenant-scoped operations without a valid tenant context are rejected.

## Authorization

The authorization model is:

```text
Authentication
      +
Tenant Membership
      +
Role
      +
Permission
      +
Resource Scope
```

Permission names use the `resource.action` convention.

## AI runtime

```text
Application
   ↓
AI Gateway
   ↓
Provider Adapter
   ↓
LLM Provider
```

Execution context may include tenant, employee/agent, knowledge, memory and permission scopes. Provider-specific business logic remains outside the core application.

## Customer product

The Customer Portal covers dashboard, agents/employees, conversations, knowledge, usage, settings and billing entry points. All operations are tenant- and permission-scoped.

## Billing and payment

```text
Usage
 ↓
Billing Engine
 ↓
Invoice
 ↓
Payment Service
 ↓
Provider Adapter
```

Payment verification, webhook signature validation, replay protection, idempotency, refunds and failed-payment recovery are required architectural capabilities.

## Marketplace boundary

Marketplace is **architecturally defined in V1.4 but not implemented in V1.4**.

The planned boundary is:

```text
Developer
 ↓
App
 ↓
App Version
 ↓
Publication
 ↓
Tenant Installation
 ↓
Granted Permissions
 ↓
Runtime Invocation
 ↓
Usage Event
 ↓
Billing / Revenue
```

Marketplace must never bypass tenant isolation or RBAC.

## Migration strategy

Migrations proceed in dependency order:

1. Identity / Tenant foundation
2. Membership / RBAC
3. Tenant ownership on core entities
4. Runtime tenant context
5. Knowledge isolation
6. Conversation isolation
7. Run / Worker isolation
8. Usage
9. Billing
10. Payment
11. Marketplace

Every migration requires forward migration, compatibility/backfill strategy, validation and appropriate rollback consideration.

## Testing

Required testing layers include unit, integration, API, tenant-isolation, runtime, billing/payment, marketplace and production-readiness tests.

Mandatory security/consistency checks include cross-tenant access rejection, authorization denial, AI context isolation, worker isolation, payment callback verification, webhook idempotency, usage idempotency and auditability.

## Status vocabulary

- **PLANNED:** defined by the Blueprint but not implemented.
- **AS-BUILT:** evidenced in the current repository.
- **VERIFIED:** implemented and validated by appropriate tests/checks.

A design document alone does not qualify as VERIFIED.

## Freeze decision

V1.4 is the frozen architectural baseline. The next permitted activity is documentation review and reconciliation in GitHub. Implementation remains downstream of that gate.
