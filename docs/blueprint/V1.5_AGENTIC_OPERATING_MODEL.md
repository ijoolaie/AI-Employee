## Executive decision

The platform is **Agent-first, not Employee-first**.

A business capability is modeled as work that can be executed by either a Human or a specialized Agent. The same task, workflow, permissions, tools, outputs, approvals and audit rules apply regardless of executor.

```text
                         WORK
                           |
                 +---------+---------+
                 |                   |
              HUMAN                AGENT
                 |                   |
                 +---------+---------+
                           |
                     SAME WORK ITEM
                           |
             +-------------+-------------+
             |             |             |
           Tools       Knowledge      Policies
             |             |             |
             +-------------+-------------+
                           |
                       Execution
                           |
                    Result + Audit
```

## Core domain concepts

### WorkItem

The canonical unit of executable work.

A WorkItem contains:

- tenant scope
- capability/task type
- input and output contracts
- priority
- risk classification
- assigned human and/or agent
- execution mode
- approval policy
- tool policy
- deadline/SLA
- parent workflow
- execution history
- audit metadata

### AgentDefinition

Reusable definition of a specialized agent:

- identity and purpose
- instructions
- capabilities/skills
- allowed tools
- knowledge sources
- memory policy
- model policy
- permission policy
- constraints
- triggers
- schedules
- handoff rules
- approval requirements
- cost budget
- evaluation policy

### AgentInstance

A tenant-scoped deployed instance of an AgentDefinition. It owns configuration, credentials references, memory, usage and run history without duplicating the reusable definition.

### HumanExecutor

A user or workforce member authorized to execute the same WorkItem capabilities. Human execution must use the same permission, approval, audit and output contracts as agent execution.

### AgentTeam

A reusable group of specialized agents coordinated around a business outcome.

### Workflow

A deterministic or agent-orchestrated sequence of WorkItems. Any node may be executed by a human, agent or both.

## Execution modes

Every executable capability supports:

- `HUMAN`
- `AGENT`
- `HUMAN_AND_AGENT`
- `AUTO`

The platform must also support delegation/fallback:

```text
Human -> Agent
Agent -> Human
Agent -> Agent
Human -> Human
```

## Approval model

Approval is policy-driven, not executor-driven.

Examples:

- low-risk read: auto
- customer reply: agent or human
- financial action above threshold: agent prepares -> human approves -> execution
- security-sensitive change: human approval required

## UX principle

The user should choose the desired outcome, not understand the runtime internals.

Examples:

```text
Create Order
[ Do it myself ] [ Let an Agent do it ]
```

```text
Resolve Support Ticket
[ Take over ] [ Ask Agent to handle ] [ Collaborate ]
```

The UI exposes complexity progressively: business outcome first, executor second, advanced agent configuration only when needed.

## Test Center

The main dashboard of every workspace must expose a Test Center. It is an operational testing surface, not a developer-only page.

The Test Center must provide role-appropriate access to:

- API health checks
- Authentication/session checks
- Tenant isolation checks
- RBAC/permission checks
- Agent smoke tests
- Tool-call tests
- Workflow tests
- Human handoff tests
- Approval tests
- Knowledge/RAG tests
- Memory tests
- Integration connectivity tests
- Webhook/idempotency tests
- Usage metering tests
- Billing/sandbox tests
- Notification/channel tests
- Background worker/queue tests
- Model/provider tests
- E2E scenario tests
- Test run history and evidence

Dangerous or production-mutating tests require explicit environment selection, dry-run support and approval gates. Test data must be isolated from production business data.

## Security invariants

1. Agent permissions never exceed the effective permissions of its execution context.
2. Tenant isolation applies equally to humans and agents.
3. Agent-to-agent calls are authenticated and authorized.
4. Tool credentials are never exposed directly to the model unless explicitly required by a secure adapter.
5. High-risk actions require policy-based approval.
6. Every execution is auditable.
7. Usage and cost are attributable to tenant, agent, workflow and WorkItem.
8. Human takeover must preserve the complete execution context and audit trail.

## Migration from Employee-centric implementation

Existing Employee entities and APIs are retained temporarily for compatibility. New execution capabilities must use Agent/WorkItem abstractions. Existing employee-backed features are migrated incrementally through adapters rather than a destructive rename.

Target direction:

```text
Legacy Employee
      |
      +--> organizational identity / compatibility

AgentDefinition --> AgentInstance --> WorkItem --> Execution
HumanExecutor ----------------------^             |
                                           Tools / Policy / Audit
```

## Acceptance criteria

V1.5 is an **architecture baseline**. It becomes an implementation-complete architecture only when the acceptance criteria below are satisfied by code and evidence; those criteria must not be confused with the current release certification state.

- every supported capability has a WorkItem contract
- human and agent execution paths share the same authorization boundary
- workflows support executor substitution and handoff
- agent definitions and instances are separated
- approvals are policy-driven
- tool access is scoped
- usage/cost is attributable
- Test Center exists in Platform, Reseller and Client workspaces
- test evidence is persisted and auditable
- legacy Employee paths have a migration strategy
