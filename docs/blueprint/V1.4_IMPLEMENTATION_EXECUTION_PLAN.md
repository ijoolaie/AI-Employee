# V1.4 Implementation Execution Plan

**Status:** READY FOR EXECUTION
**Baseline:** Frozen V1.4 Blueprint
**Rule:** This document defines execution order; it does not itself implement runtime changes.

## 1. Objective

Translate the frozen V1.4 architecture into verified implementation in dependency order while preserving existing repository behavior and avoiding duplicate architectural systems.

## 2. Execution gates

```text
Frozen Blueprint
      ↓
Repository Baseline Audit
      ↓
Foundation / Migration Gaps
      ↓
Tenant + RBAC Enforcement
      ↓
Core Runtime Alignment
      ↓
Customer/Admin Runtime Alignment
      ↓
Usage/Billing/Payment Alignment
      ↓
Developer / Marketplace Boundary
      ↓
Integration Tests
      ↓
Production Readiness
```

## 3. Phase A — Baseline audit

Before changing code, record current state as:

- AS-BUILT
- PARTIAL
- MISSING
- VERIFIED

Audit targets:

- database schema and Alembic history
- tenant ownership on business resources
- authentication and RBAC enforcement
- API contracts
- AI gateway/runtime
- workers and queues
- knowledge/RAG
- conversations
- customer portal
- admin console
- usage
- billing
- payment/webhooks
- observability

No duplicate subsystem is created where an existing repository boundary already satisfies the requirement.

## 4. Phase B — Foundation enforcement

Order:

1. Tenant context
2. Membership/RBAC
3. Resource-level authorization
4. Tenant-aware repository/service boundaries
5. API enforcement
6. Worker context propagation

Acceptance criteria:

- cross-tenant read/write is rejected
- unauthorized mutations are rejected
- tenant context is available to service and worker execution
- privileged actions are auditable

## 5. Phase C — Core runtime alignment

Order:

1. Employee/Agent lifecycle
2. Run lifecycle
3. AI Gateway
4. Knowledge/RAG scope
5. Conversation scope
6. Worker/retry/idempotency behavior
7. Usage telemetry

Acceptance criteria:

- every execution has deterministic tenant scope
- provider failures are normalized
- retries are safe
- usage/cost telemetry is associated with execution

## 6. Phase D — Customer/Admin alignment

Customer Portal:

- dashboard
- employees/agents
- conversations
- knowledge
- usage
- settings
- billing visibility

Admin Console:

- platform administration
- tenant administration
- audit visibility
- operational controls

Acceptance criteria:

- UI permissions match server authorization
- no frontend-only security decisions
- tenant boundaries are enforced server-side

## 7. Phase E — Monetization/Billing/Payment

Reuse the existing billing/payment architecture.

Order:

1. Plans/entitlements
2. Usage events
3. Subscription state
4. Invoice state
5. Payment transaction state
6. Webhook verification/idempotency
7. Failed-payment recovery

Acceptance criteria:

- entitlement changes are server-authoritative
- duplicate webhooks do not duplicate effects
- forged success callbacks cannot activate paid access
- usage retries do not double count

## 8. Phase F — Developer/Marketplace boundary

Marketplace is implemented only after its prerequisites are verified.

Order:

1. Developer identity
2. App metadata
3. App version
4. Requested permissions
5. Publication state
6. Tenant installation
7. Granted permissions
8. Runtime invocation
9. Usage event
10. Billing/revenue integration

Acceptance criteria:

- installation is tenant-scoped
- permissions are explicit
- runtime invocation cannot bypass RBAC
- usage is metered exactly once
- uninstall/revocation prevents further execution

## 9. Phase G — Verification

Required suites:

- unit
- integration
- API
- tenant isolation
- authorization
- runtime end-to-end
- billing/payment
- webhook replay/idempotency
- marketplace installation/invocation
- observability
- recovery/failure paths

## 10. Definition of Done

A phase is complete only when:

1. implementation exists;
2. migration/backfill is complete where required;
3. API/runtime integration is complete;
4. security and tenant isolation are tested;
5. observability is present;
6. failure/retry behavior is tested;
7. relevant documentation is updated;
8. verification evidence exists.

## 11. Explicit prohibition

Do not begin Marketplace implementation merely because the Marketplace boundary exists in the Blueprint. It remains downstream of foundation, runtime, billing/payment and verification gates.

## 12. Next executable step

**Phase A — Repository Baseline Audit.**

The next implementation task is to inspect the current repository and produce an evidence-backed gap matrix before modifying runtime code.
