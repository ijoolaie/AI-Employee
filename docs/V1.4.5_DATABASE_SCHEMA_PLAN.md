## Release context

`v1.4.4` is the current stable release baseline. This document defines persistence work for `v1.4.5`.

## Objective

Prepare the persistence foundation for SaaS multi-tenancy, Vendor -> Reseller -> Client hierarchy, commercial entitlements and explicit lifecycle states.

## Core Entities

### tenants
- id
- name
- status
- tenant_kind (`vendor` | `reseller` | `customer`)
- parent_tenant_id
- created_at / updated_at

### users
- id
- tenant_id
- email
- role
- status

### plans
- id
- owner/scope
- name
- status
- billing_cycle
- limits
- feature_entitlements

### subscriptions
- id
- tenant_id
- plan_id
- status
- billing_cycle
- starts_at
- expires_at / grace_until

### usage_records
- id
- tenant_id
- metric
- amount
- period

### api_keys
- id
- tenant_id
- key_hash
- scope
- expires_at

### lifecycle / audit data
Lifecycle transitions may be represented by existing resource status fields plus immutable audit records; do not create a separate lifecycle table unless a concrete resource requires historical state storage beyond audit.

Required audited transitions include:
- tenant provisioning
- plan/entitlement changes
- suspension/reactivation
- ownership/admin changes
- stop/cancel/archive/delete
- authorization-sensitive administrative actions

## Data Rules

- Child tenant ownership is explicit through `parent_tenant_id`.
- Client-controlled tenant identifiers must never determine authorization.
- Tenant hierarchy and access are validated server-side.
- Hard deletion of tenants is not the default; retention/offboarding policy must be defined first.
- Usage and quotas are always attributed to the owning tenant and applicable subscription/entitlement.

## Migration Strategy

1. Add SaaS tables without breaking existing production.
2. Introduce tenant hierarchy and lifecycle fields gradually.
3. Backfill existing records.
4. Introduce plan/subscription linkage and entitlements.
5. Enable tenant enforcement.
6. Add lifecycle/audit regression coverage.

## Success Criteria

- Zero data leakage between tenants.
- Parent/child access is explicit and tested.
- Entitlements can be evaluated server-side.
- Auditable usage tracking.
- Subscription-ready architecture.
- Lifecycle transitions are deterministic and idempotent.
